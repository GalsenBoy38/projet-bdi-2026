1. Comprendre FestiBed en une page

FestiBed vend des « packs » indissociables : des Pass de festival + des hébergements pour ce même festival. Ce n'est ni une billetterie seule, ni un site de réservation d'hébergements seul. Le cœur évalué est la gestion de données : transactions ACID, concurrence d'accès, contraintes et performance sur un gros volume (≥ 100 000 réservations).

ConceptCe qu'il faut retenir pour la modélisation
FestivalIssu du jeu public (3 136 manifestations) ou complété par un Organisateur. Possède une localisation, une période (dates à compléter : la source ne donne parfois que le mois), un quota de Pass alloué à FestiBed, un prix.
PassDroit d'accès d'une personne pour toute la durée du festival (pas de Pass partiel). Disponibles = quota − Pass déjà réservés.
ÉtablissementLieu physique du jeu public (hôtel, camping, village de vacances, résidence, PRL, auberge collective). Un Hébergeur peut en gérer plusieurs.
HébergementOffre réservable dans un établissement : type, capacité, prix, options, description, photos, périodes de disponibilité. Jamais rattaché à un festival : il apparaît dans les recherches s'il est libre toutes les nuits du festival et proche.
PanierSélection temporaire, possible sans authentification. Par festival : nb de Pass + hébergements dont la capacité totale ≥ nb de Pass. Chaque élément expire au bout de 15 min (paramétrable). Ne bloque rien.
RéservationProduit de la validation du panier (authentification obligatoire à ce moment). Re-vérification transactionnelle, puis création de la réservation, des Pass PDF et des bons d'hébergement PDF. Paiement non développé mais présent dans le modèle.

Les trois acteurs

ActeurInterface / authentificationFonctions obligatoiresFonctions bonus
FestivalierFrontOffice ; réseau social (Firebase optionnel), exigé seulement à la validationRechercher festival ; rechercher hébergement ; ajouter au panier ; valider le panier ; noter festival / établissementModifier le panier
OrganisateurBack-Office ; compte interneGérer le quota de Pass (sans toucher aux Pass réservés)Compte ; gérer / désactiver un festival ; statistiques hebdomadaires

Attention : le kickoff (diapo 5) classe tout le Back-Office en « bonus », alors que le cahier des charges rend obligatoires « Gérer le quota de Pass » et « Retirer un hébergement ». Le modèle de données doit couvrir tous les acteurs ; seul le développement des écrans bonus est conditionné à la validation des attentes principales.

Les 4 scénarios à rendre jouables (et testables)

  1. Jeff / Musilac (Aix-les-Bains, AD211) : 2 Pass + 1 emplacement 2 personnes au Camping International du Sierroz (présent dans la source) → 2 Pass + 1 bon d'hébergement.
  2. Samantha / expiration : recherche depuis Autun, fin juillet ; la sélection expire après 15 min.
  3. Samantha / concurrence : Jazz à Couches (BD054) + Hôtel des Arcades (Autun) ; une réservation concurrente fait échouer la validation ; repli sur Saint Rock (BD064) → test d'intégration de concurrence.
  4. Ronald : nouveau festival, quota 50 ; les hébergements existants apparaissent automatiquement s'ils sont libres et proches → aucune association festival ↔ hébergement.

3.3 Règles de qualité appliquées (vérifiées automatiquement par le générateur)

  1. Noms tous distincts (entités, associations, attributs) : d'où nom_festival, nom_commune, libelle_domaine… et non plusieurs nom ou libelle.
  2. Chaque entité a un identifiant (souligné).
  3. Attributs élémentaires (atomiques) : les colonnes multivaluées des sources (autres communes, soutiens) deviennent des associations.
  4. Dépendance fonctionnelle directe et élémentaire de chaque attribut vis-à-vis de l'identifiant : les informations géographiques sont sorties de FESTIVAL, la nature de l'unité d'accueil est portée par la typologie.
  5. Le formalisme graphique n'est pas suffisant : chaque entité, association et attribut est décrit textuellement (nom, sémantique, domaine, contraintes) au § 8.3.
  6. Qualités d'un modèle (cours « Introduction ») : fidélité au cahier des charges (vocabulaire identique), cohérence (un seul référentiel génère MCD, MLD et MPD), complétude par rapport aux scénarios (sans viser l'exhaustivité).

3.4 Processus : ce que le cours attend pour les BPMN du 22/10

  • D'abord un texte structuré (« Modéliser un processus ») : une ligne = une tâche, commençant par l'acteur, avec un verbe d'action au présent et à la voix active ; un processus de base puis ses variantes (panier vide, sélection expirée, Pass ou hébergement devenu indisponible, capacité insuffisante, utilisateur non authentifié).
  • BPMN dans un vrai outil BPMN qui produit un fichier .bpmn (Camunda Modeler / bpmn.io recommandé) — pas Visio ni draw.io.
  • Règles : un unique événement de début par unité ; plusieurs fins nommées par cas ; une entrée/une sortie par tâche ; pas de séquencement entre pools, messages uniquement entre pools ; toute fourche a une question, des conditions sur ses sorties et une jonction ; tâches à l'infinitif, événements au participe passé.
  • « Valider un panier » : sous-processus Transaction (BPMN avancé) avec événement d'annulation en bordure et tâches de compensation ; « Ajouter un élément au panier » : expiration de 15 min modélisée par un minuteur (branchement sur événement ou événement en bordure).
  • Acteurs à représenter (au sens MOF) : externes = Festivalier, Organisateur, Hébergeur, fournisseur d'authentification ; internes = IHM Festivalier, IHM Back-Office, serveur FestiBed, base Oracle (dépôt de données).

5. Règles métier → où et comment les garantir

Le cours (« Contraintes d'intégrité ») rappelle que certaines contraintes ne sont pas exprimables dans le MCD mais le sont presque toutes au niveau physique (SQL, triggers, ou au pire le langage hôte). Principe retenu : tout ce qui peut être déclaratif est porté par la base, le reste par une transaction du service avec verrouillage explicite.

Règle (cahier des charges)MécanismeMise en œuvre
Pas de Pass sans hébergement ni l'inverse ; capacité totale ≥ nb PassCardinalités + serviceSELECTION (1,n) SELECTION_HEBERGEMENT ; RESERVATION (1,n) PASS et (1,n) BON_HEBERGEMENT ; contrôle Σ capacite_hebergement ≥ nb_pass_selection à l'ajout et à la validation.
Un Pass couvre tout le festivalModèlePASS ne porte aucune date : il hérite de la période du festival.
Hébergement disponible toutes les nuits du festivalRequête + serviceUne PERIODE_DISPONIBILITE couvre [date_debut_festival, date_fin_festival[ et aucune NUITEE n'existe sur ces nuits.
Pas de double réservation d'un hébergementContrainte BDRelation technique NUITEE, PK (id_hebergement, date_nuit) : la seconde transaction concurrente échoue (unicité) et est annulée.
Pas plus de Pass que le quotaContrainte BDCHECK (nb_pass_reserves BETWEEN 0 AND quota_pass) + incrément du compteur dans la transaction de validation.
Quota non réductible sous les Pass réservésContrainte BDMême CHECK ; version_festival (verrou optimiste) pour les éditions concurrentes.
Hébergeur : ne pas retirer / fermer une période réservéeService + verrouSELECT … FOR UPDATE sur HEBERGEMENT puis refus s'il existe une NUITEE future hors des nouvelles périodes ; retrait = statut_hebergement = 'RETIRE'.

Re-vérification à la validationTransaction§ 9 : verrous en ordre déterministe, contrôles, insertions, commit ou rollback complet.
Signaler des festivals proches (même mois)RequêteAvertissement non bloquant + NOTIFICATION CHEVAUCHEMENT_RESERVATIONS.
Désactivation d'un festivalTransactionstatut_festival = 'DESACTIVE' ; réservations ANNULEE ; suppression des NUITEE ; NOTIFICATION ; paiements REMBOURSE ; hébergements inchangés.
Paiement prévu dans le modèleModèleCOMMANDE (0,n) REGLER PAIEMENT, statut NON_GERE dans le prototype.
Notation après le séjourContrainte + serviceIdentifiant (festivalier, festival) / (festivalier, établissement) ; CHECK valeur BETWEEN 1 AND 5 ; inclusions Merise/2 CI-I1, CI-I2 vérifiées par le service.

7. Choix de modélisation et hypothèses

ChoixJustification
Un hébergement = une unité réservable« Un même hébergement peut être réservé pour plusieurs festivals lorsque les périodes ne se chevauchent pas » : une seule réservation à la fois par nuit.
Une réservation = un festival ; une validation de panier crée une COMMANDE regroupant N réservations« Toute réservation … pour un même festival » et « un panier peut contenir plusieurs festivals ». La COMMANDE porte date, montant et paiement ; la validation reste atomique.
BON_HEBERGEMENT et PASS sont des entitésDocuments PDF numérotés du cahier des charges ; prix et dates figés au moment de la réservation (historique).
Compositions (1,1)PHOTO et PERIODE_DISPONIBILITE n'existent pas sans leur hébergement, SELECTION sans son panier, PASS et BON_HEBERGEMENT sans leur réservation : destruction en cascade (cours, « Composition »).
Spécialisation ETABLISSEMENT → CAMPING, VILLAGE_VACANCES (X)Attributs propres à ces typologies ; exclusives, non totales, définies par un attribut → T3 (cf. § 8.6).
Spécialisation COMPTE_INTERNE → ORGANISATEUR, HEBERGEUR (T)Tout compte interne a au moins un rôle ; une personne peut cumuler les deux → T1, qualité des données.
FESTIVALIER hors de COMPTE_INTERNEAuthentification externe, comptes de test, cycle de vie différent.
NUITEE (relation technique, absente du MCD)Traduction physique de la contrainte de non-chevauchement (CI2) en unicité déclarative ; ≈ 300 000 à 450 000 lignes (MOD).
Redondances maîtrisées : nb_pass_reserves, note_moyenne_etablissement, nb_notes_etablissement« Optimisation des coûts » du cours (dé-normalisation, duplication) : éviter d'agréger 100 000+ lignes à chaque recherche ; mises à jour dans la même transaction. Seules entorses à la 3FN, documentées.
Intervalles [début, fin[Nuits d'un festival du 19 au 20 = nuit du 19 ; hypothèse : un festival d'un jour réserve une nuit.
Identifiants techniques sauf codes officielsLes codes sources ne sont pas fiables ; COMMUNE (INSEE), DEPARTEMENT et TYPOLOGIE_ETABLISSEMENT gardent un code naturel.
Statut FESTIVAL : BROUILLON / ACTIF / DESACTIVEUn festival importé reste BROUILLON tant que dates et prix manquent (CHECK).

8. Modèles de données

Notation du cours : MCD — entités en rectangles (identifiant souligné, attributs avec leur domaine), associations en cartouches arrondis avec leurs éventuels attributs, cardinalités (min,max) côté entité, (1,1) = composition, losange + flèche = spécialisation (X exclusion, T totalité), cercle jaune = contrainte entre associations (Merise/2). MLD — relations avec types, clé soulignée, flèche de la relation référençante vers la relation référencée étiquetée « clé externe = clé ».

{{DICO}}

Contraintes d'intégrité non exprimables graphiquement

  1. CI1 — cohérence capacité : pour une SELECTION (et une RESERVATION), Σ capacite_hebergement des hébergements liés ≥ nombre de Pass.
  2. CI2 — non-chevauchement : deux BON_HEBERGEMENT non annulés d'un même HEBERGEMENT n'ont pas de nuit commune (→ NUITEE au niveau logique).
  3. CI3 — disponibilité : les nuits d'un bon sont incluses dans une PERIODE_DISPONIBILITE de l'hébergement ; les périodes d'un hébergement ne se chevauchent pas.
  4. CI4 — période : date_arrivee/date_depart d'un bon = dates du festival de la réservation au moment de la réservation.
  5. CI5 — quota : nombre de PASS des réservations CONFIRMEE d'un festival = nb_pass_reserves ≤ quota_pass.
  6. CI6 — hébergement retiré : un HEBERGEMENT RETIRE n'entre dans aucune nouvelle SELECTION et ne peut être retiré s'il a des nuits futures réservées.
  7. CI7 — festival désactivé : toutes ses réservations sont ANNULEE et chaque festivalier concerné reçoit une NOTIFICATION.

Quand ?

  • Référentiels et données publiques : chargés une fois au démarrage du projet, rechargeables (script d'import idempotent).

  • COMMANDE, RESERVATION, PASS, BON, NUITEE : créés à chaque validation (pic avant l'été) ; jamais supprimés (annulation logique) ; archivage annuel des éditions terminées (les NUITEE passées peuvent être purgées).
  • NOTE_* : après la date de fin du festival ; agrégats recalculés à chaque note.

Vérification de la normalisation

  • FN1 : aucun attribut non atomique (autres communes, soutiens, options, photos, hébergements d'une sélection → relations dédiées).

8.7 MPD Oracle et optimisation

Le MPD (out/sql/mpd_oracle.sql) traduit le MLD : types, PRIMARY KEY, FOREIGN KEY, contraintes nommées (CONSTRAINT …), CHECK pour les sous-types de domaines et les contraintes inter-attributs, identifiants GENERATED BY DEFAULT AS IDENTITY, colonne virtuelle pass_disponibles. Les tables sont créées dans l'ordre des dépendances (tri topologique).

Vérification effectuée sur H2 en mode Oracle : les 35 tables et leurs 144 contraintes se créent sans erreur ; avec le scénario de Jeff inséré, la base refuse un 3e Pass pour un quota de 2 et une baisse du quota sous les Pass réservés (CK_FESTIVAL_4), la réservation d'une nuit déjà prise (PK_NUITEE) et une mention « village » sur un camping (CK_ETABLISSEMENT_5). Le script reste à rejouer sur l'instance Oracle du projet.

9. Transactions et concurrence déduites du modèle

BEGIN  -- Oracle READ COMMITTED + verrous explicites, une seule transaction (@Transactional du service)
 1. Charger le panier ; ignorer les sélections expirées ; si vide → échec "panier vide"
 2. Pour chaque festival (trié par id_festival : ordre fixe = pas d'interblocage) :
      UPDATE FESTIVAL SET nb_pass_reserves = nb_pass_reserves + :n
       WHERE id_festival = :f AND statut_festival = 'ACTIF'
      -- 0 ligne → festival indisponible ; violation du CHECK → plus assez de Pass
 3. Pour chaque hébergement (trié par id_hebergement) :
      SELECT ... FROM HEBERGEMENT WHERE id_hebergement = :h AND statut_hebergement = 'PUBLIE' FOR UPDATE
      vérifier qu'une PERIODE_DISPONIBILITE couvre [date_debut_festival, date_fin_festival[ ; vérifier CI1
 4. INSERT COMMANDE, RESERVATION(s), PASS (×n), BON_HEBERGEMENT(s)
 5. INSERT NUITEE pour chaque nuit   -- violation de PK = nuit prise par un concurrent
 6. INSERT PAIEMENT (statut_paiement = 'NON_GERE') ; supprimer le panier (cascade sur ses sélections)
COMMIT -- toute erreur aux étapes 2 à 6 ⇒ ROLLBACK complet, message explicite au festivalier

Deux niveaux de protection : les verrous (FOR UPDATE, UPDATE conditionnel) sérialisent les validations concurrentes sur les mêmes ressources sans bloquer les autres ; les contraintes déclaratives (CHECK quota, PK de NUITEE) garantissent la cohérence même si un chemin de code oublie un contrôle. SERIALIZABLE est déconseillé sous Oracle (ORA-08177 sous charge). En BPMN, cette transaction correspond au sous-processus « Transaction » de « Valider un panier » (§ 3.4).

Test attendu : N threads valident simultanément le même hébergement / festival → exactement un succès, les autres échouent proprement, base cohérente (scénario 3).
